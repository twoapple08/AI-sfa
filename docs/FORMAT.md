# 관찰한 SFA 구조

근거: 사용자가 제공한 `01_base`부터 `09_tween.sfa.sfa`까지 9개 샘플, 완성 화면, MP4와 현재 앱 사용 설명. 현재 앱 버전 번호는 아직 확보하지 않았습니다. 이 문서는 공식 전체 명세가 아닙니다.

## 컨테이너와 요소

9개 샘플 모두 ZIP 안에 XML 하나가 있습니다. 이중 `.sfa.sfa` 확장자는 컨테이너 내용을 바꾸지 않았습니다.

| 요소/속성 | 관찰 |
|---|---|
| Sequence | Name, FrameCount, RatioX, RatioY, HeightWidthRatio, BackgroundColor |
| Frame | ID, 0부터 시작하는 Position, BackgroundColor |
| LayerDef | ID, Name, Visible, Locked |
| AO | 도형 요소. ID, TypeId, Color, LayerId, DrawOrder, ThicknessScale, ObjectScale, Glow 관련 속성 |
| AP | 좌표점. ID, Flags, Index, X, Y |
| AC | ConnPtId로 같은 프레임의 AP 참조 |
| FR | 채우기 영역. Color |
| FS | 채우기 경계. Kind, ObjId, StartPtId, EndPtId, StartT, EndT |

TypeId 1은 직선, 2는 원, 3은 곡선으로 화면과 대응합니다. 삼각형/사각형은 여러 직선과 연결 참조로 구성됩니다. 곡선의 정확한 수학식은 미확인입니다. 미리보기는 이차 베지어를 가정합니다.

기본 스틱맨: AO 10개(원 1개 + 직선 9개), AP 20개입니다. AP 개수는 고유한 신체 관절 수와 다릅니다. 같은 위치의 여러 끝점이 AC로 연결됩니다.

## 비교 결과

- 02_arm: 기본과 비교해 AP 한 곳의 좌표만 변경.
- 03_position: AP 20개가 동일한 X/Y 변화량으로 이동.
- 05_same: 기본과 좌표가 동일하지만 프레임·도형·점 식별 번호 등은 다름.
- 06_shapes: AO 10개, AP 21개, TypeId 1/2/3. 연결된 선 도형 포함.
- 07_custom: AO 7개와 FR 1개/FS 3개. 별도 비트맵 파일 없음.
- 08_layers: LayerDef 2개, AO 20개. 각 AO에 레이어 번호와 색상 기록.
- 09_tween: 5개 Frame, 프레임마다 AO 10개/AP 20개. 같은 AO ID가 프레임 사이 유지되며 AP ID는 달라짐.
- 첨부 MP4: 1920×1080, 24FPS, 실제 5프레임, 길이 약 0.208333초. 사용자가 재생/트위닝을 모두 24로 설정했다고 설명했으므로 추가 보간이 없는 조건.

## 좌표와 표시의 가정

미리보기는 X/Y를 각 축 0~100 비율로 취급합니다. 프레임 밖 좌표를 허용합니다. 가로세로 비율을 적용한 뒤 원의 두 점을 지름 양 끝으로 취급합니다. 정확한 앱 렌더러 검증은 남아 있습니다.
색상은 관찰된 음수/양수 값을 모두 32비트 ARGB로 해석합니다.

## 트위닝 및 커스텀

사용자 설명:

- 재생 FPS: 원본 프레임의 초당 재생 수.
- 트위닝 FPS: 보간을 포함해 보이는 초당 프레임 수.
- 두 값이 같으면 추가 보간 없음. 재생 24 / 트위닝 48이면 중간 프레임 생성.
- 커스텀 가져오기는 SFA 첫 프레임을 사용. 커스텀 제작 UI는 이 프로젝트의 초기 범위에서 제외.

현재 9개 XML에서 명시적인 FPS/트위닝 설정을 찾지 못했습니다. 이 설정의 저장 위치, 보간 함수, 생성/삭제/변형 시 대응 규칙은 아직 미확인입니다. AO ID의 지속성만으로 트위닝 규칙을 확정하지 않습니다.

## 다음 검증 순서

1. roundtrip 파일을 현재 앱에서 열어 외형과 편집 가능 여부 확인.
2. 48프레임 wave_test를 재생 24/트위닝 24에서 확인.
3. 이후 필요할 때만 동일 원본의 재생 24/트위닝 48 결과나 APK 저장/재생 코드로 보간 동작 확인.
4. 자연어 → 간결한 동작 명령 → 결정적인 프레임 생성 → SFA 변환 구조 개발.

Flags의 비트 의미, 글로우·굵기·스케일 계산, 레이어/그리기 순서 우선순위, FR 경계의 곡선 처리도 추가 확인 대상입니다. 도구는 기존 XML의 알 수 없는 속성/요소를 삭제하지 않습니다. ZIP 부가 파일·주석·XML 공백/바이트 배열까지 보존하는 포렌식 복제 도구는 아닙니다.

## 추가: 실제 사용자 작품 2개 분석 (2026-10-14)

표기 순서는 **(트위닝 FPS, 재생 FPS)** 입니다. 이번 두 작품은 모두 (60, 12) 설정으로 인코딩했다고 사용자가 설명했습니다.

| 원본 | XML 이름 | 원본 프레임 | 대응 영상 | 영상 FPS | 영상 프레임 | 길이 |
|---|---|---:|---|---:|---:|---:|
| Anonymous user file-1.sfa | 연습 | 122 | 1000326557.mp4 | 60 | 610 | 10.166667초 |
| Anonymous user file-2.sfa | 팡 | 90 | 1000326558.mp4 | 60 | 450 | 7.5초 |

첨부 순서와 길이/프레임 수의 일치로 대응을 판단했습니다. 두 영상 모두 원본 프레임 수 × (60/12) = 영상 프레임 수이고, 영상 길이는 원본 프레임 수 / 12입니다. 이 조건에서는 다섯 배의 출력 프레임 수가 확인되지만, 개별 구간 보간 방식이나 끝 프레임 처리 규칙 전체까지 입증하지는 않습니다.

추가 발견:

- 첫 작품에는 Frame 하위 TweenLink(ID, From) 10개가 있습니다. 트위닝 관련 대응 정보로 추정하지만 정확한 참조 방향과 의미는 미확인입니다. 삭제하지 않고 보존합니다.
- 두 작품 모두 프레임마다 레이어 3개를 포함합니다.
- FS Kind=0에서 StartPtId/EndPtId=-1과 0~1 사이 StartT/EndT 값이 관찰됩니다. 점 ID가 없는 경계 위치 표현으로 추정합니다.
- FS Kind=1은 점 ID 없이 ObjId만 갖는 경우가 있습니다. 두 번째 작품에는 Contour 속성도 있습니다. 정확한 의미는 미확인입니다.
- 초기 검사기는 모든 FS에 실제 점 ID가 있어야 한다고 가정했으나 실제 앱 출력과 맞지 않아, 위 두 표현을 허용하도록 수정했습니다. 다른 존재하지 않는 참조는 계속 오류로 처리합니다.
- 두 작품에도 명시적인 FPS 설정은 보이지 않습니다.

제공받은 작품 원본과 영상은 저장소에 올리지 않고 분석 근거만 기록했습니다.

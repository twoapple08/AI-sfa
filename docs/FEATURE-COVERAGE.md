# Stick Fighter 전체 기능 분석 범위와 최적화 기준

## 목표
애니메이션 창작에 쓰이는 모든 앱 기능을 목록화하고, UI 조작 → 내부 데이터 → 저장 파일 → 재생/출력 결과를 연결한다. 일부 기능 이름이나 문자열 발견은 구현 이해 완료가 아니다. 현재는 부분 분석 단계다.

커스텀 제작 UI를 별도 앱에 복제하는 것은 보류하지만, 기존 오브젝트의 외형·연결·색·굵기·변형을 처리하는 데이터 기능은 분석 범위에 포함한다. 사용자가 요청한 변형과 색상 기능을 핵심 범위로 취급한다.

색상/늘리기 등 이름이 비슷한 조작도 동일하다고 가정하지 않는다. 특정 점/도형/연결 그룹/프레임 전체 중 무엇에 적용되는지 각각 확인한다.

1. 현재 앱에서 실제 옵션 이름과 설정 범위를 확인한다.
2. 기준점과 적용 대상, 다른 기능과의 상호작용을 파악한다.
3. 내부 코드 또는 통제된 전후 샘플로 저장 표현을 확인한다.
4. 파일 재저장과 앱 표시/재생을 비교한다.
5. AI가 사용할 명령/제약과 실패 조건을 정의한다.
6. 검증되지 않은 부분은 미확인으로 남긴다.

색 변화와 변형처럼 애니메이션 중 달라지는 속성은 정지 화면뿐 아니라 프레임 간 결과를 검증한다. 앱 전체 이해도를 임의 퍼센트로 표현하지 않는다.

## 오브젝트 수 최적화 원칙
- 원이나 곡선 한 개, 기존 요소의 굵기·좌표·스케일 변경으로 같은 표현이 가능하면 우선 검토한다.
- 불필요한 중복·정확히 겹친 요소는 삭제 후보지만, 색/알파/채우기/참조 관계 때문에 결과가 달라질 수 있으므로 안전성 확인 후 병합한다.
- 연결을 끊거나 TweenLink/채우기 경계를 손상시키는 병합은 허용하지 않는다.
- 단순히 객체 개수만 최소화하지 않는다. 도형 수, 좌표점 수, 곡선, 채우기 경계, 글로우, 프레임 수와 실제 렌더링 시간을 함께 평가한다.
- 원본 프레임의 도형 재사용과 런타임/메모리에서의 재사용을 구분한다. SFA가 프레임마다 상태를 저장해야 하는 경우 무작정 데이터 생략을 하지 않는다.
- 스미어, 잔상, 파편 등 필요한 표현에는 추가 객체를 허용한다. 일률적인 강제 상한 대신 장면별 예산과 품질 목표를 둔다.
- 단계: 생성 → 중복/구조 검사 → 변형 기반 단순화 후보 → 전후 시각 비교 → 성능 측정 → 채택.

품질과 비용을 실제로 비교하기 전에는 '오브젝트 수가 줄어 더 최적화됐다'고 확정하지 않는다.

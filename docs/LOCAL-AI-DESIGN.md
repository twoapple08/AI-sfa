# 로컬 애니메이션 AI 설계 초안

## 사용자 요구

- 별 1개 이상인 Sakugabooru 자료를 학습 자료 후보로 사용.
- 원어 태그, 한국어 별칭(smears → 스미어), 자연어를 함께 입력.
- 기술 태그와 애니메이터 관련 스타일 조건을 동작 생성에 활용.
- Android APK로 배포하고 사용자 기기의 CPU/GPU/RAM을 활용.
- 우선 Stick Fighter 파일 형식·FPS·트위닝·굵기 분석을 진행.

## 구현 상태

- 현재 저장소는 파일 도구와 검증용 코드다.
- 학습된 모델, 자연어 이해 모델, 동작 생성 신경망, Android 앱은 아직 없다.
- 분석한 코드와 샘플을 이 채팅에 제공하는 것은 배포할 별도 모델의 가중치 학습이 아니다.

완전 이해를 퍼센트로 주장하지 않는다. 파일 읽기/쓰기, 좌표/도형, 레이어, 색/굵기, 채우기, 트위닝, 가져오기, 영상 출력별로 코드 근거와 앱 비교 검증을 기록한다.

## 권장 구성

1. 입력 정규화: 한국어/영어 태그를 canonical ID로 통합. 원문 자연어는 그대로 보존.
2. 소형 로컬 언어 모델: 자연어에서 캐릭터·행동·시간·카메라·기술·스타일 조건을 추출. 모든 프레임 XML을 직접 출력하지 않는다.
3. 참고 동작 검색: 검수한 동작 데이터에서 관련 사례와 스타일 특징을 검색.
4. 동작 생성기: 키포즈, 구간 시간, 이동 경로, 변형/스미어/효과 도형을 생성. 초기에는 절차적 동작과 검색을 사용하고, 데이터가 준비되면 전용 모델을 평가.
5. 결정적 엔진: 관절 연결, 도형 ID, 유효 좌표, FPS 시간축, 선 굵기, 파일 저장을 처리.
6. 미리보기·수정·검사 후 SFA 출력. 모델이 잘못된 명령을 내면 구조 검사와 범위 검사로 거절/수정.

로컬 언어 모델 + 절차적 동작만으로 특정 애니메이터 수준의 창작이 보장되지는 않는다. 무게감, 타이밍, 카메라, 효과와 변형을 표현하는 전용 동작 데이터와 평가가 필요하다.

## 태그 입력 계약 예시 (설계이며 현재 실행 기능 아님)

```json
{
  "description_ko": "빠르게 달려가 펀치하고 타격 순간만 스미어를 넣어 줘",
  "tags": [{"id": "smears", "weight": 1.0}],
  "style_reference_ids": [],
  "timing": {"tween_fps": 60, "playback_fps": 12},
  "duration_seconds": 3
}
```

- 한국어 라벨과 원어 canonical ID를 따로 보관한다.
- 기술, 행동, 효과, 애니메이터, 작품 메타데이터를 구분한다.
- 태그는 권장 조건이지 성공을 보장하는 마법 명령이 아니다. 가중치의 실제 효과는 모델 학습/평가가 있어야 한다.
- 명시적 태그와 자연어가 충돌하면 생성 전 충돌을 표시한다. 태그만/자연어만/둘 다를 모두 허용할 계획이다.
- 애니메이터 태그가 있는 영상의 모든 프레임이 해당 애니메이터의 정답 스타일이라는 가정은 하지 않는다. 불명/추정 표기를 보존한다.

## 데이터 준비

- Sakugabooru 사이트는 이번 직접 조회에서 520 응답으로 열리지 않았다.
- 검색에서 smears 태그와 API 문서는 확인했지만, '별 1개'가 작품 총점/개인 별점/선별 표식 중 무엇인지는 아직 확인하지 못했다.
- 임의로 score >= 1 조건으로 변환하지 않는다.
- 수집기나 일괄 다운로드는 아직 실행하지 않았다.

학습 데이터 한 항목에는 원본 post ID/URL, 수집 날짜, 선별 근거, 원어 태그와 종류, 출처, 사용 조건 확인 상태, 클립 구간, 중복 그룹, 추정 애니메이터 여부, 추출한 동작과 검수 상태를 기록한다.

- 영상 → 샷 분할 → 캐릭터 추적 → 포즈/이동/카메라 분리 → 스미어·가림·효과·타이밍 검수 → 대상 스틱맨으로 변환 → 동작/태그/설명 쌍 생성 순서가 필요하다.
- 일반 포즈 추정 결과를 그대로 정답으로 사용하지 않는다.
- 애니메이션에서는 극단적 변형과 가림이 핵심 표현일 수 있다.

SFA 원본은 영상과 편집 데이터의 쌍을 만드는 데 도움이 된다. 별점은 동작 품질이나 태그 정확도를 보장하지 않으며, 같은 클립·작품의 유사 장면이 학습/평가 세트에 동시에 들어가지 않도록 나눈다.

사이트 접근 가능 여부와 콘텐츠의 학습·모델 배포에 필요한 이용 조건 확인은 별도다. APK 분석 허가가 타인의 영상 자료 이용 허가를 대신하지 않는다.

## 로컬 실행과 학습

- 로컬 추론: 이미 준비된 모델로 기기에서 생성. 요청당 API 과금 없이 가능하나 전력·메모리·저장공간·시간 비용은 존재.
- 학습: 모델 가중치를 갱신. 대규모 영상 전처리와 학습은 개발 측 외부 GPU 환경을 사용하는 방식을 권장한다. 일반 사용자 폰에서 전부 처음부터 학습시키지 않는다.
- 로컬 LLM도 내부적으로 토큰을 사용한다. API 토큰 과금이 없어지는 것과 토큰 연산 자체가 없어지는 것은 다르다.
- GPU/NPU 사용 가능 여부와 메모리는 기기/드라이버/모델에 따라 달라진다. CPU fallback과 기기별 벤치마크가 필요하다.
- 사용자의 폰과 PC 자원이 자동으로 합쳐지지 않는다. PC를 별도 로컬 서버로 연결하는 모드라면 명시적으로 설계한다.
- APK와 모델 파일을 분리 배포해 APK 크기와 업데이트 비용을 줄이는 방식을 우선 검토한다. 다운로드 후 오프라인 실행 목표.

기본 권장안: 오프라인 동작 엔진 + 소형 로컬 입력 모델, 고사양 PC에서 더 큰 모델 선택, 원할 때만 외부 고품질 생성 옵션. 완전 오프라인 요구가 확정되면 외부 옵션은 제외한다.

## 비교

| 구성 | 장점 | 한계 |
|---|---|---|
| 전부 폰에서 실행 | API 요금 없음, 오프라인, 입력이 기기에 머묾 | 발열/배터리/메모리, 모델 크기와 품질 제약 |
| PC 로컬 실행 | 더 큰 모델과 긴 장면 처리 가능 | PC 필요, 하드웨어 편차 |
| 서버 실행 | 성능과 모델 관리 통일 가능 | 운영비, 연결 필요, 전송 지연 |
| 선택적 혼합 | 기본 로컬과 고품질 확장 선택 | 구현/테스트 복잡성 증가 |

## 다음 단계

1. APK 근거를 앱 실제 결과와 비교해 FPS·기본 굵기·트위닝 검증 범위 확정.
2. 별점 의미를 실제 화면 또는 post 예시로 확인.
3. 소량의 검수한 동작/태그/설명 평가 세트부터 구축.
4. 로컬 절차적 동작 baseline → 소형 모델 평가 → 필요할 때 전용 동작 모델 학습.
5. Android 패키징과 실제 기기 메모리/발열/생성 속도 측정. APK 제작만으로 학습과 창작 능력이 생기지는 않는다.

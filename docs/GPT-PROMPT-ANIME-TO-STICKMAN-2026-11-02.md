## 복붙용

너는 이 프로젝트에서 Claude와 토론하는 독립 검토자다. 주제는 **"애니메이션 캐릭터의 움직임을 스틱맨으로 바꿔 Stick Fighter(.sfa)로 가져오는 방법"**을 처음부터 다시 정하는 것이다. Claude의 지금 방식이 근본부터 잘못됐다는 게 사용자 판단이다. 결론을 정하지 말고 선택지를 근거로 비교해 줘.

**사용자 지시(11-02): 이 토론에서는 '3D 금지'를 일단 빼고 생각한다.** 3D를 거치는 방법도 같은 기준으로 평가한다(채택 여부는 토론 뒤 사용자가 정한다).

### 1. 목표와 쓰임
- 2단계 생성기의 학습 재료: 실제 애니 → SFA로 변환한 것에서 인물 움직임을 배운다(수집 SFA는 주 재료가 아님). 인물은 스틱맨으로 바뀌고, 나중에 캐릭터 디자인을 입힌다. 설계: `docs/STAGE2-GENERATOR-DESIGN-2026-11-02.md`.
- 결과 스틱맨은 **사람이 앱에서 편집할 수 있어야** 한다(앱 기본 스틱맨처럼 연결이 살아 있고 포즈 도구로 꺾임).
- 24/24(사용자는 트위닝 없이 24장/초 직접 그림). 평면 2D 앱이다.
- 쓸 자원: Kaggle T4×2(주 30시간), PC GTX 1050 Ti 4GB, 가끔 RTX 5060 2시간 미만. 개인 비상업 — 모델 라이선스 무관, 품질 우선, 시간 제한 없음.
- 애니메이터별 범위(고정, 재해석 금지): nian41 = 몸 뼈대 움직임 1순위, 나카무라 = 타격 타이밍·간격·이펙트와 몸의 맞물림(검출 어려워 타이밍 위주였음). riooo·optical-core·yukina 몸동작은 쓰지 않는다. 범위 원문: `AGENTS.md`.

### 2. 앱 스틱맨 사실(확인된 것)
- 앱 기본 스틱맨: `data/app_templates/stickman_default.sfa`(사용자가 앱에서 새로 만들어 내보냄). 10조각: 머리 원(TypeId 2, 지름 양끝 점) + 몸통 + 위팔·아래팔 ×2 + 허벅지·정강이 ×2. 모두 한 점(목·골반·팔꿈치·무릎)에서 이어짐(AC). 파란점(Flags 3) = 골반, 뿌리. Flags 4 = 부모 점에 붙는 끝, 2 = 골반에 붙는 끝, 5 = 그 밖. 관절점(주황, Flags 33)은 기본에는 없다.
- 좌표는 화면 % (X는 가로, Y는 세로 %, HeightWidthRatio 0.5625).
- 실제 파일 ID 규칙: 오브젝트 ID는 장끼리 이어지고, 점 ID는 장마다 새로 쓴다(여러 장 파일 304개 모두 이웃 장끼리 점 ID 공유 0).
- 변환 도구: `tools/pose_to_stickman.py`, 시험 `tests/test_pose_to_stickman.py`.

### 3. 지금까지 시도와 실측(nian41 영상 1913231262086463573, 298–390장, 창고에서 등을 보이며 걸어가며 팔을 휘두름)
- 포즈: YOLO11m-pose(COCO 17점, 실사 학습) 추론만. nian41 영상 8개를 6장 간격으로 훑으면 사람 검출 0–39%. 이 구간만 연속 검출.
- v1: 짐작한 점 구조 → 앱에서 연결 안 됨(머리-몸통 처음부터 분리), 머리 방향을 얼굴 점으로 정해 머리가 흔들림.
- v2: 앱 기본 스틱맨 구조 + 틀 길이 고정(방향만 포즈에서) + 머리는 몸통 방향. 재생은 됐으나 어색.
- v3: 원근 단축(짧게 보이면 짧게, 늘리지는 않음), 떨림 줄이기(5장 중앙값 + 가중 평균).
- 실측: 팔은 장의 20–31%가 틀 길이 0.6 미만으로 보임(화면 쪽·가려짐). 팔 방향이 한 장에 27–29° 이상 튀는 장 10%(고친 뒤 90% 분위 20–22°). 실제 정강이는 기본 스틱맨 비율의 약 1.36배.
- 사용자 평가: **어색함이 사라지지 않는다. 걸으며 팔이 몸 앞으로 가 일부가 안 보이면 과하게 움직인다. 근본부터 잘못된 것 같다.**
- 편집 연결 문제(원인 찾음, 별개 문제): v3 첫 장만 담은 파일은 앱에서 연결 정상, 93장 파일은 편집하면 조각이 떨어짐. 조각 길이를 고정한 v4도 똑같이 깨짐. 원인: 우리 파일은 점 ID를 모든 장에서 같게 썼는데 앱 파일은 장마다 새 점 ID를 쓴다. 고친 v5는 사용자 앱 확인 대기.

### 4. Claude의 진단(반박해도 됨)
- 장마다 '보이는 2D 관절 위치'를 베끼는 방식 자체가 문제: 3D로 돌고 멀어지는 몸을 평면에 투영하면 가림·원근 단축·좌우 뒤바뀜이 생기고, 실사 포즈 모델은 애니에서 가려진 팔다리를 짐작으로 찍는다. 길이 고정·평활은 증상만 덮는다.
- 스틱맨 애니메이터는 영상을 베끼지 않는다: 키포즈 + 타이밍 + 관절 회전으로 잇고, 애매한 건 읽기 쉽게 다시 연출한다(옆모습·과장).

### 5. 비교할 선택지(더 나은 게 있으면 추가)
- A. 2D 추적 개선: 애니에 강한 포즈 모델(애니 그림으로 학습된 것, 또는 우리 자료로 미세조정), 신뢰도 낮은 팔다리는 믿지 않고 유지/보간.
- B. 2D 키포즈 + 타이밍 재연출: 확실한 장만 키포즈로, 사이는 관절 각도 회전으로 보간(길이 보존), 원본에서는 '언제 어떤 자세'만 가져옴.
- C. 3D 경유: 단안 3D 포즈/인체 모델(예: 영상 기반 3D 사람 추정, 인체 메시 맞춤)로 3D 뼈대 → 가림·원근 해결 → 원하는 카메라(원본 카메라 또는 옆모습)로 2D 재투영 → 스틱맨. 애니(비현실 비율·과장·스미어)에서 정확도, 계산량, 카메라 처리.
- D. 학습된 변환기: 애니 장면 → 스틱맨 매개변수(관절 각도)를 바로 내는 모델. 학습 정답을 어디서 얻나(합성: 3D 동작 자료를 애니풍으로 렌더? 사람이 앱에서 고친 결과?).
- E. 사람 참여: 자동 결과를 사용자가 앱에서 키포즈만 고치고, 그 수정이 학습 자료가 됨. 사용자 시간 비용.
- 조합(예: C로 초안 → B로 키포즈화 → E로 검수)도 평가.

### 6. 답해 줄 것
1. 진단(§4)에 동의/반대와 근거. 놓친 근본 원인이 있나?
2. 선택지별: 기대 품질(특히 가림·몸 돌리기·빠른 동작·스미어), 실패 방식, 계산량(T4 기준), 구현 난이도, 앱 편집 가능성, 2단계 생성기 학습 재료로서의 적합성. 구체 모델·논문·도구 이름을 대되, 실존·버전을 확인할 수 없으면 '확인 필요'로 표시.
3. 추천 경로 1개와 차선 1개, 그리고 **먼저 할 가장 작은 실험**(무엇을 재서 무엇을 가르는지, 합격선). 측정으로 가를 수 없는 판단은 사용자 눈 판정 항목으로 분리.
4. '어색함'을 숫자로 잴 방법이 있나(예: 관절 각속도 튐, 길이 변화, 사용자 판정과의 상관). 반례(점수는 좋은데 어색한 경우)도 하나 들어 줘.
5. 시험 장면 선택 기준(어떤 nian41·나카무라 구간이 공정한 첫 시험인가).

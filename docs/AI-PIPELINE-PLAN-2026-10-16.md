# 애니메이팅 AI 단계별 설계안 — 2026-10-16

사용자 학습 방식(2026-10-16) 기준의 실행 설계다. **아직 구현을 시작하지 않았다.** 이 설계는 기존 초안 [LOCAL-AI-DESIGN](LOCAL-AI-DESIGN.md), [MOTION-EXTRACTION](MOTION-EXTRACTION.md)을 대체·확장한다. 앱 동작 근거는 [APP-UNDERSTANDING-STATUS](APP-UNDERSTANDING-STATUS-2026-10-16.md)를 따른다.

## 확정된 사용자 결정

- **용도:** 오직 개인용이다. 스틱파이터 개발자와도 이야기된 사항이다. 수집 자료·추출 데이터·모델은 공개하지 않는다(기존 공개 금지 원칙 유지).
- **학습 자료:** SFA가 아니라 웹의 애니메이션 작화 클립(주: Sakugabooru 등)과 영화 장면이다.
  - **서양 카툰(톰과 제리류)은 학습 대상에서 제외한다(사용자 결정 2026-10-16).** 수집기는 `western` 태그 클립을 받지 않고 통계에서도 뺀다(`EXCLUDED_TAGS`).
  - 영화는 카메라 연출과 연출 방식 자체(예: 스피드스터 표현)를 참고하는 서브 자료다.
  - 사용자 SFA 작품은 스틱파이터다운 표현을 맞추는 보정용으로 받는다(사용자 준비 예정).
- **추출 대상:** 인체 관절점, 파편·이펙트의 형태(외곽선), 배경 움직임, 색감. 촬영·편집 단계의 효과(집중선, 화면 왜곡 등)는 **영상 전체가 아니라 해당 부분만** 제외한다.
- **프롬프트:** 태그 + 자연어. 태그 종류는 요소(wind, fire), 기술 연출(rotation, camera_movement, background_animation), 명명된 기법(smears, impact_frames, yutapon_cube), 애니메이터 이름(스타일, 혼합 가능)이다.
  - 작품명은 학습하지 않는다.
  - 애니메이터 스타일은 자료가 많은 유명 애니메이터만 대상으로 한다. artist_unknown은 스타일 조건으로 쓰지 않는다.
  - 한국어는 나중에 별도로 한다. 지금은 영어 태그만.
- **출력:** 사용자 기기(Android APK, Windows EXE)에서 로컬 실행한다. 입력은 프롬프트·(트위닝, 재생)·길이, 출력은 SFA다. 객체 기반이라 뭉개짐이 없다.
- **카메라:** 스틱파이터에는 카메라가 없다. 애니메이션처럼 카메라가 움직인 결과를 프레임마다 다시 그린다(좌표 변환을 객체에 반영).
- **캐릭터:** 기본은 전신 스틱맨이다. 손 등 클로즈업은 실제 애니 캐릭터의 일부처럼 윤곽·채우기 객체로 묘사할 수 있다.
- **진행 순서(레이어 쌓듯):** ① 캐릭터 1–2명 동작 → ② 이펙트·파편 → ③ 배경·카메라 → ④ 스타일 태그·애니메이터. 각 층이 동작한 뒤 다음 층으로 간다.

## 전체 구조

```
[수집] 클립+태그 메타데이터 ──▶ [전처리] 샷 분할·정지/원화 판별·편집효과 마스크
      ──▶ [추출] 관절점·이펙트 외곽선·카메라·배경·색 ──▶ [정규화] 공통 표현(JSON)
      ──▶ [학습] 태그/자연어 → 공통 표현 생성 모델 ──▶ [변환] 공통 표현 → SFA
      ──▶ [검사] sfa_render로 렌더·자동 평가 ──▶ [앱] APK/EXE 로컬 추론
```

이미 있는 것: SFA 읽기·쓰기·검사(`sfa.py`), 앱과 같은 시간축·보간(`sfa_tween.py`), 앱 출력과 거의 같은 렌더러(`sfa_render.py`, 실제 작품 평균 MAE 0.91/255). [변환]과 [검사]의 바닥은 준비돼 있다.

## 공통 표현(초안)

SFA를 직접 학습하지 않는다. 다음과 같은 작은 구조를 학습한다.

- `characters[]`: 프레임별 2D 관절 17–21개(머리 중심·반지름, 목, 어깨, 팔꿈치, 손목, 손끝, 골반 중심, 엉덩이, 무릎, 발목, 발끝) + 가시성/신뢰도 + 앞뒤(깊이 순서).
- `camera`: 프레임별 2D 변환(이동·확대·회전) + 흔들림 성분.
- `effects[]`: 형태 원시(선/곡선/원/다각형 채우기) + 색·알파·glow 추정 + 수명(생성·소멸 프레임) + 같은 객체 유지 ID(보간 짝).
- `background`: 배경색, 큰 움직이는 배경 요소.
- `timing`: 원본 컷의 홀드 패턴(1s/2s/3s 작화), 대상 (T, P).
- `tags`: 클립 태그(작품명 제외), 애니메이터 태그(유명 대상만).

변환기는 이를 SFA 객체로 바꾼다(스틱맨 리그 생성, 연결 AC, 레이어, ID 유지로 트위닝 짝 보장, [실용 규칙](APP-UNDERSTANDING-STATUS-2026-10-16.md#생성-ai에-주는-실용-규칙지금까지의-근거) 적용).

## 현실적 어려움의 해결 방안

### 1. 애니메이션 관절 추적이 자주 틀림

- **여러 검출기 앙상블:** 실사용 모델(RTMPose/DWPose/ViTPose)과 일러스트용 모델(bizarre-pose-estimator)을 함께 돌린다. 서로 일치하는 점만 채택하고 불일치는 "불확실"로 표시한다.
- **시간축 보정:** 점 추적(CoTracker3)으로 프레임 사이를 잇는다. 뼈 길이 일관성·좌우 바뀜 검사·짧은 결측 보간을 한다. 단, **스미어·임팩트 프레임은 평활화하지 않는다.** 의도된 변형이므로 태그와 함께 보존한다.
- **작은 수정 도구 + 반복 학습(active learning):** 불확실한 프레임만 사람이 빠르게 고치는 간단한 UI를 만든다. 고친 수백~수천 프레임으로 검출기를 애니메이션에 맞게 미세조정하고 반복한다. 사용자의 수정 노력이 가장 효율적으로 쓰이는 지점이다.
- **다인물:** 인물 검출·추적(ByteTrack 계열)으로 ID를 유지한다. 겹치는 구간은 불확실로 남긴다.

### 2. 이펙트·파편을 선/채우기 객체로 바꾸기

- **영역 분리:** SAM 2 영상 분할로 이펙트·파편 영역을 프레임 사이에 추적한다(대상 지정은 자동 후보 + 필요 시 클릭).
- **윤곽 → 원시:** 윤곽 추출 후 단순화(Douglas–Peucker)한다. 이를 스틱파이터 원시(직선, 이차 Bézier, 원, 구멍 있는 채우기)로 맞춘다. 원시 개수와 오차를 함께 최소화한다.
- **색:** 영역 평균색 → 채우기색, 외곽 밝기 퍼짐 → glow 반경·두께 추정. 렌더러로 다시 그려 원본과 비교하는 **역렌더 최적화**로 미세조정한다. 앱과 같은 렌더러가 있으므로 가능하다.
- **시간 연결:** 같은 파편은 같은 ID를 유지해 트위닝 짝이 되게 한다. 생기고 사라지는 것은 수명으로 기록한다.

### 3. 편집 효과 부분 제외(영상 전체가 아니라 그 부분만)

- 집중선·속도선: 방향성 직선 검출로 마스크.
- 화면 흔들림·카메라 셰이크: 배경 전체 움직임(전역 변환)으로 분리해 `camera`의 흔들림 성분으로 기록한다. 그리는 대상이 아니라 카메라로 처리한다.
- 블러·왜곡·색수차: 국소 광학 흐름의 비정상, 경계 번짐으로 마스크.
- 플래시·전체 색 반전: 프레임 전체 밝기 급변으로 표시한다. 필요하면 배경색 변화로 재현할 수 있다.
- 마스크된 부분은 추출에서 빼되, 그 시간에 무엇이 있었는지(예: 임팩트 순간)는 태그·이벤트로 남긴다.
- 처음엔 규칙 기반으로 시작하고, 수정 도구로 모은 라벨로 작은 분류기를 학습해 점점 개선한다.

### 4. 애니메이터 스타일

자료 수가 충분한 애니메이터만(예: 클립 수 상위) 대상으로 한다. 각 애니메이터의 특징을 공통 표현의 통계로 요약해 조건으로 쓴다. 통계는 타이밍(홀드 패턴), 스미어 빈도, 이펙트 형태, 카메라 성향 등이다. 한 클립의 모든 프레임을 그 사람 정답으로 보지 않는다(공동 작업 가능성).

### 5. 원화·정지샷

- **정지샷·팬(한 장 그림 + 카메라 이동):** 프레임 차이가 거의 없거나, 전역 변환만으로 설명되면 "정지 + 카메라"로 분류한다. 카메라 무빙 학습 자료로 쓰고, 동작 자료로는 키포즈 1장으로만 쓴다.
- **원화(선화, 色 없음):** 선이 선명해 관절 추적이 오히려 쉽다. 포즈·형태 자료로 쓰고 색 학습에서는 제외한다. 원화 모음은 보통 키포즈만 있어 간격이 크므로, **키포즈 → 중간 동작** 학습(인비트윈 모델)의 정답 쌍으로 쓴다. 같은 컷의 완성 영상이 있으면 짝지어 타이밍까지 학습한다.
- **홀드(같은 그림 반복, 2s/3s 작화):** 오류가 아니라 타이밍 정보다. 홀드 길이를 기록해 (T, P) 설정과 함께 학습한다. 예: 24fps 2s 작화 ≈ 재생 12.

## 단계별 실행 계획

### 사양 가변 원칙(사용자 지시 2026-10-16)

사용하는 PC 사양은 매번 다를 수 있다. GTX 1050 Ti(4GB)일 때도, RTX 4070/4080/5060일 때도 있고 RAM 양도 달라진다. 따라서 **어떤 단계도 특정 사양을 전제하지 않는다.**

- **실행 시 자동 감지:** 각 작업 시작 때 GPU 종류·VRAM·RAM·CPU 코어·저장공간 여유를 감지해 기록한다. `hardware_profile.json`으로 남기고, 결과물에도 어떤 사양에서 만들었는지 적는다.
- **사양별 프로필:** 감지 결과에 따라 모델 크기(소/중/대), 배치 크기, 해상도, 동시 처리 수, 혼합 정밀도(FP16/BF16)를 자동으로 고른다.

| 등급(예) | 예시 | 기본 선택 |
|---|---|---|
| 저 | VRAM ≤4GB | 작은 검출 모델, 배치 1–2, 일부 단계 CPU, 긴 클립은 나눠 처리 |
| 중 | VRAM 8–12GB | 중간 모델, 앙상블 2개, 생성 모델 학습 기본 크기 |
| 고 | VRAM ≥16GB | 큰 모델·앙상블 전체, 더 큰 생성 모델, 빠른 반복 |

- **중단·재개:** 모든 긴 작업은 클립 단위·학습 체크포인트 단위로 저장한다. PC가 바뀌거나 꺼져도 이어서 할 수 있다. 같은 결과를 다시 만들지 않는다(이미 처리한 클립은 건너뜀).
- **결과 호환:** 사양이 달라도 공통 표현 형식과 SFA 출력은 같다. 저사양에서 만든 데이터를 고사양에서 이어 쓰고, 반대도 가능하게 한다. 고사양일 때 저사양 데이터만 골라 다시 처리하는 옵션을 둔다.
- **메모리 부족 시 자동 강등:** 실행 중 VRAM/RAM이 부족하면 배치·해상도·모델 크기를 한 단계 낮춰 재시도하고, 그 사실을 기록한다.
- **앱(7단계)도 같은 원칙:** 사용자 기기 성능을 감지해 모델 크기와 생성 길이 한도를 정한다.

### 0단계 — PC 준비(사용자, PC 복귀 시)

사양은 위 원칙대로 매번 자동 감지한다(이전 기록: i7-8700 / GTX 1050 Ti 4GB / 16GB, 다른 때는 RTX 4070·4080·5060 등). 가장 낮은 4GB VRAM에서도 다음이 가능하다.

- 관절 추적·분할의 **추론**: 대부분 가능하다. 큰 모델은 작은 버전을 쓰거나 느리게 돌린다.
- 작은 동작 생성 모델(수백만~수천만 파라미터)의 **학습**: 가능하다. 시간은 걸린다.
- 대규모 학습이나 큰 언어 모델 미세조정: 어렵다. 필요하면 그 단계만 클라우드 GPU를 쓴다.

준비 체크리스트:

1. Windows 업데이트, NVIDIA 드라이버 최신화.
2. 저장공간 **200GB 이상** 여유. 클립 수천 개 + 추출 데이터용이며 SSD 권장.
3. 설치: Git, Python 3.11, ffmpeg, (선택) VS Code. CUDA는 PyTorch 설치 시 함께 받는다.
4. `git clone` 이 저장소 → 가상환경 생성. 패키지 목록과 설치 스크립트는 1단계 시작 때 제공한다.
5. Claude Code를 PC에서 쓰거나, 이 클라우드 세션과 병행한다. 무거운 처리는 PC, 문서·코드는 어디서든 가능하다.

### 1단계 — 수집기(소규모)

- Sakugabooru API로 태그 메타데이터를 먼저 받는다(영상 없이). 태그 분포와 애니메이터별 클립 수를 집계한다.
- 그다음 대상 태그로 클립 **수백 개**만 받는다(예: fighting, punch, kick, running + 대표 애니메이터). 요청 간격을 지키고 같은 클립 중복을 제거한다.
- 메타데이터 보관: post ID, 태그(종류별), 애니메이터, 길이, 해상도, 수집일. 작품명 태그는 저장하되 학습 입력에서 제외한다.

수집 도구 검토(사용자가 받아 온 제미나이 제안, 2026-10-16):

- 채택: Sakugabooru 공식 API(`post.json`, `tag.json`)와 gallery-dl(Moebooru 지원)을 수집 기반으로 쓴다.
- 우선 확인: 허깅페이스의 기존 Sakugabooru 데이터셋(제안된 이름 `trojblue/sakugabooru2025`). 존재·규모·태그 포함 여부를 확인하지 못했다. 쓸 수 있으면 직접 수집을 크게 줄인다.
- 보조: Bilibili·Catsuka는 yt-dlp를 쓴다(쿠키 사용은 필요할 때만). Eyecandy는 요청 간격을 지키는 소규모 크롤러를 쓴다.
- 제외 또는 수동 참고만: ShotDeck·Frameset·Flim(유료·약관). 
- 제안의 성공 확률 %는 근거가 없어 쓰지 않는다.
- 제안 예시 스크립트의 보완점: 페이지 넘김, 재시도·이어받기·중복 제거, 스트리밍 다운로드, **tag.json으로 태그 종류(artist/copyright/general/meta) 구분 저장**(작품명 제외·애니메이터 스타일에 필요), `source`는 제목이 아님, 사양 자동 감지·재개 원칙.
- 저장 형태: 클립별 `영상 + post.json(태그 종류별)` + 전체 인덱스 CSV.
- 메타데이터 우선 집계(영상 없이)는 PC 없이도 가능하다. 단 클라우드 환경 네트워크 허용 도메인에 사이트를 추가해야 한다.

### 2단계 — 층① 캐릭터 동작

샷 분할 → 정지/원화/홀드 판별 → 관절 추출 → 앙상블·시간 보정 → 수정 도구 → 공통 표현 저장.

변환기(공통 표현 → 스틱맨 SFA)와 렌더 검사를 만든다. **이 시점에 "영상을 스틱맨 SFA로 옮기기"가 먼저 동작한다.** 생성 AI 이전에도 쓸모 있는 결과물이다.

### 3단계 — 첫 생성 모델

입력은 태그(+간단한 자연어)이고 출력은 공통 표현의 캐릭터 동작이다. 후보는 작은 Transformer 또는 동작 확산 모델(MDM 계열)이다. 평가는 자동 지표(발 미끄러짐, 뼈 길이 일관성, 떨림, 타이밍 분포)와 렌더 영상 육안 검토다.

### 4–6단계 — 층② 이펙트, 층③ 배경·카메라, 층④ 스타일

각각 추출기 → 공통 표현 확장 → 모델 확장 → SFA 변환 규칙 추가 순서로 진행한다. 클로즈업 묘사(윤곽 객체)는 층② 기술을 재사용한다.

### 7단계 — 앱

- 모델을 ONNX로 내보낸다. 실행은 Windows EXE(ONNX Runtime + 간단한 UI), Android APK(ONNX Runtime Mobile 또는 LiteRT)로 한다.
- 입력은 프롬프트·태그·(T, P)·길이, 출력은 SFA를 다운로드 폴더에 저장한다. 미리보기는 렌더러를 앱용으로 옮기거나 저해상도로 근사한다.
- 자연어는 1차로 태그 사전 + 간단한 규칙으로 처리하고, 필요하면 작은 로컬 언어 모델을 붙인다.

## 사용자에게 받을 것

- PC 복귀 알림과 0단계 체크리스트 결과(사양 확인).
- 보정용 SFA 작품(준비 예정).
- (2단계) 수정 도구로 불확실한 관절 프레임 검수. 분량은 처음엔 수십 클립 수준.
- 우선 다룰 동작·애니메이터 목록(선택. 없으면 클립 수 상위로 정한다).

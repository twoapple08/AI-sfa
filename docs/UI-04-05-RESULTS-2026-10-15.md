# 04 실제 편집 조작과 05 수동 트위닝 잇기

- 04의 실제 메뉴·드래그·변형 적용을 녹화와 저장 상태에 연결했고, 05는 수동 링크 하나로 다른 ID의 원이 중간에 이동하는 실제 출력을 확인했다.
- 전체 앱 기능이나 모든 조작 공식의 완료를 뜻하지 않는다.
- 사용자가 **‘굽힘’이라는 기능은 없다고 정정**했다.
- 내부 `perspective-bend` 문자열을 사용자 기능명으로 확정한 기존 안내가 잘못됐으므로 독립 굽힘 시험과 요청을 폐기한다.

- 첨부 SFA 11개 모두 기존 구조검사 오류 0. 녹화 4개는 균등 간격 접촉표 및 조작 주변 추가 표본을 검토했으며 전체 프레임의 전수검토가 아니다.
- 실제 출력 2개는 모두 1920×1080/24FPS/48장/2초, 총 96장을 800×450으로 디코딩했다.
- 픽셀 일치 언급은 이 축소 디코딩 조건에 한정된다.
- 전체 해상도 렌더 엔진 재현 검증은 아니다.
- 원본·녹화·추출 이미지는 공개하지 않는다.

체크섬·메타데이터·객체별 상태차이·변환 적합·96장 영역수치는 [UI-04-05-AUDIT-2026-10-15.json](UI-04-05-AUDIT-2026-10-15.json). 객체/점 번호는 XML 열거 순서의 0기반 번호이며 앱 ID가 아니다.

## U1 늘이기와 크기 변형을 분리

- 1000326658 약 64–73초에 색상 & 늘이기 모드의 초록 점 표시 상태에서 오른쪽 빨강 손끝을 드래그한다.
- 약 77초 이후 변형 탭에서 크기(%)를 100→200으로 올리고 굵기 100%를 유지해 ‘변형 적용’을 누른다(약 80.5–81.5초). 따라서 최종 stretch 파일은 **손끝 변경과 연결 스틱맨 전체 크기 변경이 누적된 결과**다.
- 빨강 아래팔만 2배로 만드는 단일 시험으로 해석하지 않는다.

- 최종 저장에서 스틱맨 10객체의 ObjectScale=2, ThicknessScale=1. 주황선 2개는 원래대로다.
- 스틱맨 20점 중 손끝을 제외한 19점은 정확히 허리(35,40)를 기준으로 `p'=c+2(p−c)`에 맞는다.
- 어깨(35,20)→(35,0), 머리 위(35,5)→(35,−30), 오른팔꿈치(39.21875,30)→(43.4375,20). 음수 Y는 실제 저장값이므로 삭제/캔버스 안으로 이동하지 않는다.

- 최종 오른손(63.0210441085,75.3277807630)을 같은 2배 변환의 역으로 환산하면 크기 적용 전 손끝은(49.0105220543,57.6638903815)로 계산된다.
- 이는 녹화의 손끝 이동과 부합하는 **역산값**이며 별도 중간 SFA로 직접 검증한 좌표가 아니다.
- 손끝 드래그의 내부 수학식/각도제한/모든앵커 전파를 확정하지 않는다.
- ObjectScale2가 실제 UI 크기 적용 후 보존되므로,02의입력 2→왕복 1 사례를 ‘ObjectScale 저장 불가능’으로 일반화할 수 없다.

## U2 원근과 두 번째 결과

- 첫 원근 녹화 약 25–37초에서 스틱맨만 둘러싼 사각 핸들을 변형한다.
- 주황선 2개는 저장좌표/속성 그대로이고, 스틱맨 20점의좌표가 변한다.
- TypeId/색/Flags/AC/ThicknessScale/ObjectScale은 그대로다.

- 20점 대응으로 8계수 사영변환을 최소제곱 적합하면 최대좌표오차 약 1.92×10⁻¹². 반면 일반 아핀변환 최대오차 약 3.2432다.
- **이 표본은 하나의 사영변환으로 좌표가 바뀐 상태와 수치상 일치**한다.
- 모든 핸들 동작의 변환행렬 산출식, 기준사각형 계산, 범위 밖 점/곡선/원 처리까지 확인한 것은 아니다.
- 원의 TypeId가 2로 남았다는 사실과 실제 윤곽 렌더링을 구분한다.

두 번째 녹화 약 70초에 원본을 다시 가져온 뒤 주황선과 스틱맨의 선택사각형을 조작한다. 최종 perspective2는 주황선그대로, 스틱맨 좌표가 `x'=1.188627237122304x−6.399073975019572`, `y'=1.2515268974477898y−0.1628640039895718`에 맞는다(최대오차 7.73×10⁻¹⁴). 스틱맨 10객체의 ObjectScale와 ThicknessScale은 모두 1.1820125979474732로 바뀐다.

- 첫 결과와 달리 아핀 확대·이동인 결과이며, 속성값 1.1820은 좌표배율 1.1886/1.2515와도 같지 않다.
- 이를 원근 전체의 고정 확대공식이나 굽힘으로 명명하지 않는다.
- 두 번째 조작의 핸들별 배율/굵기 계산식은미확인이다.

## U5 수동 트위닝 잇기 — 실제 출력 확인

녹화 약 55–58초 원본 12를 본 뒤 13으로 이동한다.13에서현재오른쪽원과이전왼쪽원이함께보이고, 약 63–64초두원의위쪽점사이를드래그해보라색연결표시가생긴다. 회색 이전원과 연결표시는 편집보조이며 출력대상 두원으로 오해하지 않는다.

- after의 13번째 Frame에 `TweenLink ID="뒤객체AOID" From="앞객체AOID"` 하나가 추가된다.
- 다른프레임에는없다.
- 이름과이링크를제거하면 before/after의 XML은정확히같다.
- 링크는서로다른 AOID를대응시키며앞뒤 AOID자체를병합/재할당하지않는다.
- AP의 AC를새로추가한것도아니다.

| 출력번호(1부터) | 잇기 전 흰원영역 | 잇기 후 흰원영역 |
|---|---|---|
|23|x235–327,y179–270|동일|
|24|없음(임계값초과픽셀 0)|x354–445,y179–270(933픽셀)|
|25|x472–564,y179–270|동일|

- 전체 96장 검사에서두영상의축소 RGB가다른것은 24번째한장뿐이다.23/25는왼쪽/오른쪽원이고,24는링크없으면누락,링크있으면중앙원이다.
- 임계값은각 RGB채널>180이며중앙원 위치의육안표본도확인했다.
- **동일형상·다른 ID의이두원은수동링크로중간이동이연결된다.** 다른유형/점순서/부분곡선/여러링크/충돌/역방향/FR의대응정책까지일반화하지않는다.

# SFA 뷰어(안드로이드) v0.2 — 2026-10-20

Stick Fighter 원래 앱은 SFA를 열 때 내부 DB로 옮기느라 느리고 '응답 없음'이 뜬다(사용자 보고). 그래서 보기·재생·MP4 내보내기만 하는 별도 앱을 만들었다. 편집 기능은 없다. 원래 앱의 코드는 쓰지 않았고, 우리가 분석한 파일 형식·그리기 규칙으로 새로 작성했다.

## 구성

| 파일 | 역할 |
|---|---|
| `viewer-android/` | 안드로이드 앱(Kotlin, minSdk 26). `gradle assembleRelease`로 빌드 |
| `SfaParser.kt` | SFA(ZIP 안 XML)를 형식 전용 바이트 스캐너로 한 번 읽어 숫자 배열로 변환 |
| `SfaDoc.kt` | 변환 결과와 캐시 파일(.sfab) 읽기·쓰기. 두 번째부터는 캐시로 바로 연다 |
| `FrameRenderer.kt` · `Blur.kt` | 한 프레임 그리기(아래 규칙) |
| `VideoExporter.kt` · `Yuv.kt` | 휴대폰 내장 H.264 인코더로 MP4 저장(동영상/SfaViewer) |
| `MainActivity.kt` | 열기·재생/정지·프레임 이동 막대·내보내기 화면 |
| `tools/sfa_render.py` | 서버용 기준 렌더러. 앱 내보내기 영상과 픽셀을 대조해 규칙을 정한다 |

## 그리기 규칙 (앱 영상 대조로 확인)

정적 분석(AOT-RENDER-CONTEXT·PAINT-DISPATCH·DRAW-GLOW·GLOW-BACKEND·GROUP-SHADER-TIMELINE)으로 얻은 식을 실제 앱 내보내기 영상과 비교해 확인했다.

| 규칙 | 근거 |
|---|---|
| 기준 화면 1920×(1920×비율). 여백 6px 안쪽에 비율 맞춤, `x = ox + uw·X/100` | 여백 0이면 차이가 5배 커진다. 6이 가장 잘 맞음 |
| 선 폭 `round(1.14 × 8 × ThicknessScale)`, 둥근 끝·이음 | 1.0/1.3배보다 1.14가 가장 잘 맞음 |
| ObjectScale은 선 폭에 영향 없음 | 곱하면 차이가 커짐 |
| 곡선(TypeId 3) = 2차 베지어, 원(2) = 두 점이 지름 끝 | |
| 채우기: FS의 Contour별로 조각을 이어(간격은 직선) 닫고 짝홀 규칙, 외곽(0)에서 구멍(1..)을 뺀다. 곡선 T만 0–1로 자름 | 정적 분석(AOT-FILL-PATH)과 일치. VSSG 102번 프레임 차이 58→10.6. 안드로이드는 구멍을 같은 짝홀 경로에 더하는 방식(결과 동일, Path.op는 프레임당 수 초라 사용 안 함) |
| 원 위 t: 첫 점에서 시작해 시계 방향(화면 기준) | 8가지 경우 중 최소 |
| 레이어: 목록 순서대로, 첫 레이어가 맨 아래 | 반대로 하면 VSSG가 크게 틀림(차이 6.9→0.7) |
| 레이어 안: DrawOrder순. 연결 그룹(AC로 이어진 오브젝트)마다 글로우를 먼저, 그다음 오브젝트별 채우기·선 | p3 글로우 고리 차이 2.7→1.6 |
| 글로우: 폭 `8·ThicknessScale·GlowThickness/10` 띠를 Gaussian(`sigma=√(GlowRadius²+0.29²)`)으로 흐림 × GlowColor × GlowAlpha | sigma 배율 0.5·1.5·2보다 1이 가장 잘 맞음 |

검증 수치(프레임 평균 절대차, 0–255, 영상 압축 노이즈 포함):
- 서버 기준 렌더러: 0.08–1.7
- 안드로이드 코드(Robolectric 네이티브 그래픽으로 서버에서 실행): 0.25–2.3

검증 자료: 사용자 제공 SFA 4개와 그 앱 내보내기 영상(비공개, 서버에만 둠).

## 성능 (서버 JVM 측정, 휴대폰은 다를 수 있음)

| 파일 | XML | 첫 변환 | 캐시 크기 | 캐시 읽기 |
|---|---|---|---|---|
| VSSGTOILET(114프레임, 오브젝트 45만) | 372MB | 4.2초 | 52MB | 0.4초 |
| 작은 파일(90–122프레임) | 수 MB | 0.04–0.2초 | 0.3–1.3MB | 수 ms |

- 프레임 그리기(1920×1080): 10–470ms. 큰 글로우가 많은 프레임이 느리다.
- 재생은 화면 폭 최대 1280으로 그리고, 그리기가 24fps보다 느리면 느리게 재생된다(화면에 실제 fps 표시).

## 아직 안 된 것

- 트위닝: v0.5에서 FPS(트위닝, 재생) 조정과 보간을 넣었다(아래 v0.5).
- 글로우의 세부(셰이더 끝단 cap, 링 적분, 원래 앱의 축소 래스터)는 근사다. 큰 글로우 고리에서 차이가 가장 크다(2.3).
- 실제 휴대폰에서의 설치·속도·인코더 호환은 사용자 확인이 필요하다.
- 서명: 서버의 디버그 키로 서명했다. 새 세션에서 다시 빌드하면 키가 달라져 덮어 설치가 안 될 수 있다(그때는 지우고 다시 설치).

## v0.2 변경 (2026-10-20, 사용자 휴대폰 시험 반영)

사용자 결과(v0.1): 설치·열기 됨, VSSG 첫 열기 약 12초, **오브젝트가 많은 장면에서 재생이 멈춤**, MP4 내보내기 77.2초. 앱 내보내기 영상과 뷰어 내보내기 영상을 같은 파일로 비교 제공.
- 비교 결과: 단순 장면은 거의 같았고, VSSG 96–102번 같은 겹친 그물 장면이 크게 달랐다(평균 차 27–57). 원인은 채우기 조립 규칙(끊긴 곳에서 새 윤곽을 만든 것)이었고, 앱 규칙(Contour별 윤곽·간격 잇기)으로 고쳐 10 이하로 줄었다.
- 재생: 여러 스레드로 미리 그려 JPEG 캐시(1280폭, 앱 캐시 폴더)에 저장하고, 재생은 캐시를 읽어 24fps로 보여 준다. 아직 안 그린 프레임에서는 기다린다. 캐시는 같은 파일을 다시 열 때도 쓴다.
- 내보내기: 최대 4스레드가 앞 프레임을 미리 그려 인코더에 넘긴다.
- 남은 차이: 아주 촘촘한 선 그물에서 선 위치가 국소적으로 1–3px 다른 곳이 있다(전체 변환은 같음, ECC로 확인). 원인 미확인.

## v0.5 (2026-10-20): FPS(트위닝, 재생) 조정·보간, 옛 형식 파일, 창 크기 대응

사용자 보고: (21,11)로 만든 SFA(모션작3, 56프레임, 2023년 파일)가 원래 앱에서는 5.1초 동안 부드럽게 재생되는데, 뷰어(24,24 고정)에서는 하얀 화면만 2.3초 나왔다.

### 원인 [실측]

1. **하얀 화면:** 이 파일은 옛 형식이다. `LayerDef`가 없고 AO에도 `LayerId`·`DrawOrder`·`ThicknessScale`이 없다.
   - 뷰어는 레이어 목록을 돌며 그 레이어의 오브젝트만 그렸다. 그래서 아무것도 그리지 않았다.
   - 원래 앱은 레이어 목록이 없으면 오브젝트 전체를 쓴다(AOT-OBJECT-TWEEN-PAIR).
   - 서버 기준 렌더러(`tools/sfa_render.py`)도 같은 문제가 있었다.
2. **길이와 부드러움:** SFA에는 FPS가 저장되지 않는다. Sequence 속성은 Name, HeightWidthRatio, FrameCount, BackgroundColor뿐이다.
   - 원래 앱은 (T,P)=(21,11)이면 T>P이므로 보간한다. 출력은 round(56×21/11)=107프레임, 21fps, 5.10초다.
   - 뷰어는 56프레임을 24fps로 보여 줘 2.33초였다.
   - 받은 영상 길이와 맞는다: 앱 5.07초, 뷰어 2.30초.

### 고친 것 (안드로이드·Windows 같은 코드)

- **파서:** 프레임에 `LayerDef`가 없으면 오브젝트의 LayerId 값마다 보이는 레이어를 만든다.
- **문서 구조:** AO ID(`oId`)와 AP Index(`pIdx`)를 저장한다. 캐시 버전이 2에서 3이 되어, 처음 한 번은 다시 변환한다.
- **`Timeline`:** native_timing.py와 같은 시간표다.
  - T>P이면 출력 round(N·T/P)개를 T fps로, 원본 위치는 j·P/T다.
  - 아니면 N개를 P fps로 보여 준다.
  - 미리 그리기 캐시 폴더 이름에 `t21p11`처럼 (T,P)를 넣는다.
- **보간 그리기(`render(tl, j)`)**는 분석 문서의 규칙을 따른다.
  - 오브젝트 짝은 같은 ID로 정한다. 앞에만 있거나 뒤에만 있는 오브젝트는 중간 장면에 그리지 않는다.
  - 점은 Index로 맞춘다. 같은 목록 위치를 먼저 보고, 없으면 처음부터 찾고, 그래도 없으면 앞 좌표를 유지한다.
  - 값을 섞는 방식은 다음과 같다.
    - 색: ARGB 채널마다 앞값 + round(차×t)
    - 굵기: 선형
    - 글로우 반경·두께: round
    - 글로우 알파: 앞값 + trunc(차×t)
  - 채우기 처리는 다음과 같다.
    - 후보는 바깥 경계 오브젝트가 모두 짝 있는 것뿐이다.
    - 짝을 짓는 순서: 먼저 오브젝트·윤곽·T가 모두 같은 것끼리 짓는다. 다음으로 T를 뺀 키가 양쪽에 하나뿐인 것끼리 짓는다.
    - 짝이 있으면 색과 T를 섞는다. 짝 없는 앞 채우기는 그대로 그리고, 짝 없는 뒤 채우기는 그리지 않는다.
  - 근사인 부분: 수동 TweenLink, 경계 회전·방향 정규화, AP 참조 비교는 넣지 않았다. TweenLink를 쓴 파일은 원래 앱과 다를 수 있다.
- **화면:** FPS (트위닝, 재생) 버튼을 넣었다.
  - 안드로이드: 가로 보기에서는 머리줄, 세로 보기에서는 파일 정보 카드에 있다. 1–120을 고르는 숫자 휠이다.
  - Windows: 1–240을 숫자 칸으로 넣는다.
  - 값은 파일마다 기억하고, 기본은 (24,24)다.
  - 재생 간격, 이동 막대, 시간 표시, MP4 내보내기가 모두 시간표를 따른다.
- **Windows 명령줄:** `--export 입력 출력 [T,P]`.

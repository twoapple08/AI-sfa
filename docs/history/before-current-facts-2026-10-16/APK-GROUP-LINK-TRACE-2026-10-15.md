# 그룹 Flags의 참조 인코딩과 수동 링크 경로의 경계

## 새로 확인한 내용

- 04의 그룹 저장값을 기존 APK와 대조해 큰 Flags 값의 참조 인코딩을 확인했다.
- **bit16(0x10)이 설정된 이 표본에서 `Flags >> 6`은 그룹 기준점 ID**이고, 하위 6비트는 옵션 비트를 보존한다.
- 그룹 이름이나 색이 아니라 점 참조다.
- 숫자 Flags를 불투명한 상수로 복사하거나 ID만 재할당하면 이 참조를 깨뜨릴 수 있다.
- 현재는 분석 근거만 추가했고 생성기·최적화기 수정은 없다.

자료:
- 기존 캐시 `/workspace/scratch/6d77389e706a/private/`가 존재했고, 재다운로드·재역컴파일하지 않았다.
- libapp.so SHA-256은 기존 기록과 같은 `35ce3936f08e5da6caf08e0f3d4c80e0c81777475ac4f682c66f9f4a00a32c1f`.
- Java 자료를 Flutter 전체 소스로 해석하지 않는다.
- 아래 ELF 오프셋은 SQL·문자열 위치이며 실행 함수 주소가 아니다.

## Flags — 실제 SFA와 독립 정적 근거

| 상태 | 위 선 Index0 ID | 아래 선 Index0 Flags | 해석 |
|---|---:|---:|---|
| grouped | 1462471 | 93598163 | `(1462471 << 6) \| 16 \| 3`와 정확히 동일 |
| grouped_move | 1462471 | 93598163 | 그룹 동반 이동 후 참조 유지 |
| baseline / ungrouped | 해당 파일의 독립 점 ID | 3 | 0x10 없음, 상위 참조 없음 |

- 93598163의 하위 6비트는 19(0x13), 상위 값은 1462471이다.
- 아래 점에는 위 점을 향하는 AC가 있고, 위 점에는 아래 점을 향하는 AC가 있다.
- "Flags의 그룹 값이 임의로 큰 상수"라는 해석에서는 벗어난다. 다만 Flags와 AC 중 어느 조건을 어떤 UI 연산이 먼저 읽는지는 아직 모른다.
- 단순 숫자식 일치뿐 아니라 다음 APK SQL과도 독립적으로 부합한다.

| libapp.so 파일 오프셋 | 직접 관찰한 SQL의 의미 |
|---|---|
| 0x2d16d | 점 복사·삽입문은 0x10이 켜졌을 때 상위 참조에 파라미터 오프셋을 더한 뒤 6비트 왼쪽 이동, 하위 6비트 보존. 꺼졌을 때 마스크 47(0x2f) 적용 |
| 0x357a3 / 0xa781e | root·파생 점 조회 UNION에서도 같은 참조 재매핑식. 파생 점 ID 재구성과 기준 참조를 따로 계산 |
| 0x9fad7 | 범위 내 참조일 때 상위 참조에서 기준 ID를 빼고 하위 6비트 보존. 범위 밖·플래그 미설정 분기는 0x2f 마스크 |

- 이 식들은 "상위 값을 점 ID 공간에 맞춰 재매핑하는 표현"임을 강하게 뒷받침한다.
- 해당 SQL 호출부·파라미터 역할·실행 상황을 끝까지 연결한 것은 아니다.
- 모든 Flags 상위 비트가 언제나 그룹 리더 ID라는 규칙이나, 0x2f의 모든 개별 비트 의미는 확정하지 않는다.

검증:
- grouped와 grouped_move 두 상태에서 ID 압축식 assert 통과.
- baseline/ungrouped의 Flags 3 복원 assert 통과.
- 기존 11개 SFA 구조 검사와 05 영상 96장 검사는 반복하지 않았다.

## TweenLink — 저장·실제 출력과 네이티브 함수를 구분

- 05의 Frame13 TweenLink는 뒤 AO를 ID, 앞 AO를 From으로 저장하고, 실제 중간 원 출력에 영향을 준다(별도 UI 보고서).
- Flutter AOT에는 다음 근거가 있다.

| 위치 | 의미 |
|---|---|
| 0xa8f8a | frame_tween_link 테이블: frame_id / animation_object_id / from_animation_object_id, 기본 키 (frame_id, animation_object_id) |
| 0x57b76 | 프레임 ID로 대상 AO·앞 AO를 조회하는 SQL |
| 0x8f7c3 | 프레임·대상 AO·앞 AO 3값을 삽입하는 SQL |
| 0x2b058 / 0x772c8 | resolveTweenLinks / appendTweenLinksXml 이름 |
| 0x33181 / 0x4ee21 / 0x665eb | UI 드래그 종료·시작·갱신 이름. 이름만으로 호출 관계 확정 금지 |

반면 읽은 네이티브 코드는:
- `Y2.i.d`의 두 도형 대응 분기는 뒤 프레임 map에서 앞 도형의 **같은 AO ID**로 조회한다(약 87–89 / 110–112행).
- `X2.a` / `Y2`에서 frame_tween_link / TweenLink / from_animation_object_id를 참조하는 저장·로드 코드는 찾지 못했다.
- 이 범위의 Java 로더는 raw_flags 대신 selectable과 anchor_point_type을 OR해 점 Flags를 만든다(X2.a 약 266/410행).

결론:
- 읽은 같은 ID 매칭 분기만으로는 05의 다른 ID 링크 효과를 설명할 수 없다.
- 실제 출력이 다른 렌더 경로를 쓰거나 상위 단계에서 링크를 해결할 가능성 등이 남는다.
- **05가 Flutter 렌더러라는 실행 경로를 단정한 것은 아니다.** 읽은 네이티브 함수만으로 05 결과를 설명할 수 없다는 경계를 확인했다.

## DrawOrder / ObjectScale의 원인 추적은 진행 중

- 네이티브 X2.a 약 150/381행은 DB 도형을 draw_order → ID 오름차순으로 읽는다.
- 약 190 / 389–390행은 detail의 thickness_scale / object_scale을 구분해 읽는다.
- AOT에 있는 이름: resolveDrawOrder(0x6dab5), compareDrawOrder(0x4a33b), importSequenceXmlText(0x61337), XML 속성 ObjectScale(0xa7579)과 DrawOrder(0xa1db0).
- 그러나 문자열 발견만으로 01 순위 변경 / 02 ObjectScale 2→1의 정확한 발생 함수를 확정할 수 없다.
- SFA 가져오기·내부 정규화·재내보내기의 경계를 계속 추적한다.
- FR 배치 키도 미확인으로 유지한다.

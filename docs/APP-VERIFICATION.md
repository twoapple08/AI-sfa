## 불일치의 추가 검사와 원인 후보

ffmpeg로 768프레임 전체를 순서대로 추출하고 480×270으로 축소했다. 13구간에서 파란색 분류 조건 B>120, B−R>60, B−G>40인 픽셀은 전반/후반 모두 매 프레임 1120개였다. 14구간 교차 중심 (240,135)의 RGB는 48프레임 모두 (27,88,233)으로 파란색이었다. 이 수치는 영상 디코딩·축소 결과의 관찰값이며 앱 원본 ARGB와 동일하다고 해석하지 않는다.

입력 XML에서는 13구간의 LayerDef.Visible가 601부터 false이고, 14구간의 빨간 AO.DrawOrder는 649부터 14050→14100, 파란 AO는 14060으로 유지된다. 따라서 생성 파일에 의도한 변화가 없는 문제는 아니다.

APK-ORDER-01: animation_object DB 테이블에는 sequence_id와 draw_order가 있고 frame_id는 없다. 순서 갱신도 도형 ID를 대상으로 하는 SQL 문자열이다. **같은 AO ID에 프레임마다 다른 순서를 준 시험 설계가 앱 DB와 맞지 않을 가능성**이 있다. importer가 첫 값/마지막 값/다른 값을 택하는지는 아직 미확인이다.

13구간은 DB가 프레임별 표시를 표현할 수 있음에도 출력이 다르다. importer에서 값이 유실되는지, 네이티브 출력이 표시값을 적용하지 않는지, LayerDef 표현 가정이 틀렸는지 아직 분리하지 못했다. 영상만으로 앱 오류라고 단정하지 않는다.

## FPS 가져오기 관찰 — 사용자 보고

사용자는 생성 시 FPS 설정을 바꾸어도 불러온 뒤 (60,12)로 고정되는 것으로 관찰했다. 이전 wave 가져오기 설명과 부합하지만 시험한 설정 조합·새 프로젝트/기존 프로젝트 조건·앱 설정 승계는 아직 분리되지 않았다.

이 관찰을 실사용 주의로 반영한다: 생성기 설정만 믿지 말고 가져온 뒤 두 FPS를 직접 확인/설정한다. DB DEFAULT 12 또는 last_project_* 문자열만으로 강제 초기화 경로를 확정하지 않는다. 이번 영상의 (24,24) 출력 성공과 가져오기 초기값 (60,12)는 서로 다른 단계다.

## 다음 요청: APP-V1-ROUNDTRIP 한 파일

앱에 가져온 그 합본 프로젝트를 수정하지 않고 앱에서 SFA로 다시 내보낸 파일 **1개**를 받는다. 합본 전체 영상이나 설정 화면을 다시 요구하지 않는다. 원본과 LayerDef/Visible/DrawOrder/동일 AO ID/FPS 관련 속성을 비교하여 다음 실험을 좁힌다. 재저장 파일만으로 화면 렌더러와 네이티브 출력 차이까지 확정할 수는 없다.

현재 manifest는 생성기 산출물의 대기 초기값으로 유지한다. 실제 관찰은 이 기록이 권위 있는 근거다. 생성기 재실행으로 실제 앱 결과를 덮어쓰지 않는다. 원본 영상/추출 프레임은 공개 저장소에 게시하지 않는다.

## SFA 왕복 비교 방법과 관찰

- 24프레임 전체를 XML로 읽었다.
- 세 파일 모두 매 프레임 14 AO / 28 AP / 24 AC / 3 FR / 13 FS이고, 전체 객체 태그 수도 같다.
- AO는 14개의 고유 ID가 프레임 전체에 유지되고, AP는 672개 고유 ID다.

왕복에서 바뀐 것:
- Sequence.Name과 ZIP 내부 XML 이름: 사용자 저장 이름에 맞게 변경.
- Frame/AO/AP ID: 앱 ID로 재배정. AC·FS가 그 재배정된 대상을 참조.
- DrawOrder 절대값: 재배정된 객체 ID에 맞게 변경되지만, 이번 14객체의 상대 순서는 보존.
- X/Y 숫자 표기: 23 → 23.0 같은 직렬화 형식 변경. 수치 변화 없음.
- FS의 명시적 Contour=0은 생략. Contour=1인 안쪽 경계 4개는 매 프레임 명시적으로 보존. Kind1 원 참조도 유지.

비교 방법과 결론:
- 프레임 위치·객체 순서·점 순서로 ID를 대응시키고, DrawOrder를 상대 순위로 바꿨다.
- AP 좌표는 float 수치로, AC는 연결 대상 집합으로 비교했다. 생략된 Contour는 0으로 정규화했다.
- 이 기준에서 모든 24프레임의 도형 유형·좌표·Index·Flags·레이어·색·두 배율·글로우 속성·연결 그래프·FR 색·FS 순서/객체/점/T/Contour가 같았다.
- 비교 기준은 이름·ID·숫자 문자열·절대 순서값의 바이트 동일성을 요구하지 않는다.
- AC 목록의 순서에 의존하는 미확인 알고리즘까지 증명한 것은 아니다.

설정 저장 위치:
- initial과 24_24의 XML은 Sequence.Name만 같게 놓으면 전체 직렬화가 같다.
- 이번 두 SFA의 root/frame에는 FPS나 전체 선 굵기 항목이 없다.
- 따라서 **SFA 이름만으로 설정값을 판정하지 않으며**, 이번 설정은 녹화와 실제 MP4로 확인했다.
- 앱의 모든 설정이 항상 SFA 밖에 저장된다는 일반화는 하지 않는다.

## UI 설정 기록

- 화면 녹화는 약 10초 간격 전체 접촉표와 설정 변경 주변 표본을 확인했다. 전체 3446프레임을 전수 육안 검토한 것은 아니다.
- 녹화 약 60초 / 82초의 OPTIONS: 트위닝 강도 24FPS, 재생 속도 12FPS, 선 굵기 100%.
- 약 85초에는 슬라이더 조작 중 일시적으로 25/24였고, 86–89초 표본에서 24/24로 바로잡힌 것을 확인했다. 25/24를 최종 설정이나 실패로 집계하지 않는다.
- 이름 변경, 프로젝트 SFA 재내보내기, 최종 영상 표시가 녹화에 있다. 정확한 픽셀 위치의 전체 클릭 로그를 복원한 것은 아니다.

추가 사용자 보고:
- 가져오기 직후 (60,12)일 때도 (24,12)일 때도 있고, 이유는 불명이다.
- 이번 표본에서는 (24,12)가 직접 관찰됐다. 이전의 "항상 60,12로 강제" 가정은 사용하지 않는다.
- last_project_* 문자열이 있다는 사실만으로 설정 승계가 원인이라고 확정하지 않는다.
- 기본값·마지막 사용 설정·가져오기 경로·프로젝트별 저장의 어느 조합인지는 미확인이다.
- 지금 재현 실험을 추가로 요청하지 않고, 각 시험의 가져온 직후·설정 후 기록을 축적한다.

## 실제 출력에서 확인한 것

1000326645.mp4의 24프레임을 전체 해상도 RGB로 디코딩했다. 첫 프레임 시각 검토와 각 프레임의 선택 영역 평균을 확인했다.

- 왼쪽 청록 외곽 면 안쪽에 구멍이 있다. 구멍 좌우에서는 배경이 보이고, 가운데는 앞서 저장된 붉은 띠가 보인다. 구멍 밖의 붉은 띠 위치는 청록 면으로 덮인다.
- Kind1 채우기를 가진 파란 원이 흰 윤곽과 함께 보인다.
- 기본 선 Color 알파 0인 오른쪽 선의 푸른 글로우가 보인다.
  - 기본 선이 투명하다는 것만으로 글로우도 사라진다고 판정하면 안 된다는 실제 표본 근거다.
  - GlowColor 알파 64 / GlowAlpha 128의 정확한 조합식은 이 한 표본만으로 정하지 않는다.

7×7 픽셀 영역 평균의 24프레임 집계:

| 영역(영상 픽셀 중심) | 평균 RGB | 시간축에서 영역 평균의 최대 변화(R/G/B) |
|---|---|---|
| 배경 (100,100) | (24,24,24) | 0/0/0 |
| 청록 면 (300,300) | (41,194,205) | 0/0/0 |
| 구멍 빈 부분 (410,500) | (23.24,24,24) | 1.71/0/0 |
| 구멍 뒤 붉은 띠 (485,500) | (234,64,53) | 0/0/0 |
| 구멍 밖 띠를 덮은 청록 (485,300) | (41,194,205) | 0/0/0 |
| 파란 원 중앙 (1248,540) | (48,124,239) | 0/0/0 |
| 발광 선 부근 (1498,540) | (29.42,51.27,72.86) | 2.29/1.14/1.71 |

해석의 한계:
- 원본 SFA의 RGB와 디코딩 RGB에는 작은 차이가 있다.
- 800×450으로 축소한 24장은 모두 바이트가 같지 않으며, 첫 프레임과의 최대 채널 차이는 25였다. 압축·축소의 영향을 포함하므로 실제 렌더 변화나 앱 오류로 단정하지 않는다.
- 전체 픽셀의 정확한 렌더 재현 비교가 아니며, 위 영역은 선택 표본이다.
- 이 구멍 성공만으로 현재 실행 렌더러가 Flutter라는 결론을 내리지 않는다. EVEN_ODD 등 다른 경로에서도 이 단순 형상은 같이 표시될 가능성이 있다.
- 반대 방향 윤곽 / 복잡한 Contour / 겹침 순서 / 부분 경계는 01 합본으로 따로 확인한다.

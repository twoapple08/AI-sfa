## 공식 미완료 34개의 분류 — 파일·코드

최종 로그의 `judge_end={eos:120, forced:64}`는 **4방향 184개**의 합계다. 공식 두 방향은 그 부분집합인 92개이고 미완료는 34개다. 종료 이유가 위 두 가지뿐이므로 공식 미완료 34개도 모두 `forced`다. 64개를 공식 미완료 수로 혼동하지 않는다.

| 공식 92개 중 미완료 분류 | 개수 | 의미 |
|---|---:|---|
| 한도 직전 강제 EOS | 34 | 모델이 EOS 외의 토큰을 원했지만 생성기가 종료 |
| 최대 길이에서 그대로 잘림 (`limit`) | 0 | 4방향 전체에서도 해당 종료 사유 없음 |
| OOM | 0 | 메모리 부족 없음 |
| 빈 출력 | 0 | 빈 장으로 실패한 경우 없음 |

`seq_train.generate`는 길이 2048의 64토큰 전부터 EOS가 문법상 허용되는 자리에서 EOS를 강제한다. 원래 argmax가 EOS가 아니면 `done=False, reason=forced`다. **SFA 문법을 읽지 못해 멈춘 것과 모델이 끝내지 않아 강제로 끝난 것을 구분해야 한다.** 문법 예외가 이번 실패 원인이라는 로그 근거는 없다. 원출력에는 개별 34개 생성 토큰·ID 목록이 없어, 34개 각각의 마지막 선택을 복구한 것은 아니다.

## CPU 재생성 조건과 검증

- 2회차 `best.pt`, 78709걸음. `ckpt.pt`와 같은 최종 모델이며 중간 64937 모델은 아니다.
- 정확한 `sj/judge.npz` 하나만 Kaggle에서 선택 다운로드. 판정 자료 5판·어휘·목록을 코드로 확인. 최종 판정과 같은 640폭·방향0·상한2048, 목록 앞 6장 고정. 잘 나온 그림을 선택하지 않았다.
- **CPU float32**다. 공식 Kaggle GPU 혼합 정밀도 실행을 대체하지 않으며 공식 점수를 다시 판정하지 않았다.
- 진단용 생성과 기존 `seq_train.generate`를 첫 표본에서 토큰 전체·종료 사유까지 일치 확인했다. 6개 모두 엄격 문법 검사 통과.
- 6번의 6·1058·1985번째 선택을 전체 접두열 계산과 KV 캐시 계산으로 대조했다. 세 자리 모두 argmax 일치, 문법 내 EOS 확률 차이 최대 약 `5.0e-8`. 이 세 자리에서 토큰 한 칸 밀림·캐시 누적 오차가 원인이라는 근거는 없다. 전 자리의 수학적 동일성을 증명한 것은 아니다.
- 저장된 GPU 판정 시트와 같은 480폭 렌더·270높이 행으로 대조했다. **1·2번 출력 그림은 픽셀 단위 완전히 일치**. 3~6번은 다르다. 따라서 아래 재생성 세부 수치를 GPU의 개별 원출력 수치로 대체하면 안 된다. 특히 4번은 배경·채움 차이로 평균 RGB 차이 약76이다.

## 생성 도중의 변화 — CPU 계산·그림 눈 판독

부분점수는 기존 `sfa_objscore`의 0~100 점수다. 접두 그림은 정답을 아직 덜 그렸으므로 낮은 점수 하나만으로 첫 객체가 잘못됐다고 판정하지 않는다. 원래 크기의 초기 그림도 함께 대조했다.

| 고정 표본 | 정답→최종 객체 | 25%→50%→75%→최종 부분점수 | 끝냄 |
|---|---:|---|---|
| 1 Connecting_line | 2→13 | 1.10→12.71→7.82→7.82 | 자연 |
| 2 Dudu_SPECTRUM | 10→19 | 9.76→41.93→29.60→26.48 | 자연 |
| 3 Hjll_SPECTRUM | 3→17 | 0→0→0→0 | 자연 |
| 4 Kllll_SPECTRUM | 1→24 | 0→0→0→0 | 자연 |
| 5 Rider_Coord_Fix_Part15_Pivot | 57→26 | 5.90→17.29→26.29→33.33 | 자연 |
| 6 StickFigureNew | 14→231 | 6.35→2.60→1.61→1.18 | 강제 |

- [그림 눈 판독] 1번은 초반부터 짧은 꺾인 선 정답과 위치·방향이 다르다. 3·4번도 첫 객체부터 정답의 선/원 대신 잘못된 긴 선을 만든다. 6번은 첫 객체부터 과도하게 긴 수평선이 등장한다. 종료만 빨리 시켜도 이런 초기 형상이 복구되지는 않는다.
- [CPU·눈 판독] 2번은 중간에 스틱맨 머리·몸·다리 일부가 만들어지지만, 선·곡선을 추가하면서 41.93→26.48로 낮아진다. 이 표본은 CPU 최종 그림과 저장 GPU 그림도 완전히 같다. 후반 추가 생성의 해로움이 단순 정밀도 차이만은 아니라는 직접 표본이다.
- [CPU] 6번은 정답 길이182토큰 부근에서 객체17개·15.90점이지만, 1986토큰·객체231개·1.18점까지 계속된다. 원 토큰 종류 중 CIRC 220회·LINK 299회다. 말미에는 EOS보다 LINK를 고르며 강제 종료한다. 모든 초과 객체가 새로 보이는 선이라는 뜻은 아니다. 중복 원·연결도 포함한다.
- [CPU] 5번은 후반까지 점수가 올라가지만 정답57개 중 출력26개에서 자연 종료한다. **모든 장에 같은 조기 종료 규칙을 넣으면 된다**는 결론도 성립하지 않는다.

## 정답을 끝까지 주었을 때의 종료 선택 — CPU 계산

자유 생성이 만든 틀린 접두열 때문인지 구분하려고, 같은 입력에 **정답 토큰 전체에서 마지막 EOS만 뺀 접두열**을 넣었다. 마지막 자리에서 문법 허용 후보만 남겨 비교했다. 아래 확률은 전체 어휘가 아니라 그 자리의 문법 허용 후보 안에서 정규화한 값이다.

| 표본 | 정답 끝에서 모델 선택 | EOS 확률 |
|---|---|---:|
| 1 | LINE | 0.000000206 |
| 2 | LAYER | 0.001083 |
| 3 | CURVE | 0.000455 |
| 4 | LINE | 0.000000830 |
| 5 | LINE | 0.036512 |
| 6 | LINE | 0.220089 |

6장 모두 EOS보다 추가 그리기/레이어를 고른다. 따라서 **자유 생성 중 실수 누적만으로 종료 실패를 설명할 수 없다.** 이 작은 고정 표본에서는 올바른 접두열에도 종료 선택이 약하다. 학습 전체의 EOS 오류율을 잰 것은 아니며, 학습 손실 가중·자료 분포·이미지와 좌표 읽기 중 무엇이 근본 원인인지는 추가 통제가 필요하다.

## 복붙용 프롬프트

Stick Fighter(.sfa) 애니메이션 앱용 '영상 → SFA' 변환 모델을 다시 설계하고 1판을 구현했어. 첨부를 보고 검토해 줘. 이건 Claude와의 토론이야. 동의하면 동의하고, 반대면 근거(파일:줄, 숫자, 계산)를 대 줘. 인상이나 일반론이 아니라 이 코드와 자료에 대해서만.

**배경**
- SFA는 장마다 오브젝트(직선·원·2차 곡선, 색·굵기·글로우, 레이어)와 점 연결(AC), 면(FR)으로 된 XML이고, 좌표는 화면 가로·세로의 %(0–100)야.
- 이전 설계는 '보이는 선 픽셀 지도'를 정답으로 줬다가 실패했어. 가려진 부분, 오브젝트 묶음, 연결, 레이어가 정답에서 빠졌어.
- 새 설계는 SFA를 그리는 순서대로 적은 토큰열을 정답으로 하고, 이미지 인코더 + 트랜스포머 디코더가 그 문장을 직접 써(문법 강제).

**사용자(앱 사용자 본인)가 정한 원칙 — 바꾸자는 제안은 근거가 아주 강할 때만**
1. 스파로 그린다: 출력은 처음부터 SFA 오브젝트. 픽셀 그림을 거치지 않는다.
2. 만든 파일을 원본 파일과 채점한다. 만점이면 인코딩한 영상도 같다. 파일 → 영상은 성립하지만 그 반대는 아니므로 픽셀로 채점하지 않는다.
3. 영상이 안 바뀌는 차이는 정답으로 친다: ID, 장 사이 ID 이어짐(트위닝 없이 24,24로 만듦), 면 칠 순서, 파란점, 점 방향, 겹치지 않거나 같은 색인 오브젝트끼리 순서.
4. 둥근 곳은 곡선 오브젝트. 비율은 파일 비율 그대로(앱은 파일 비율로 영상을 내보냄 — 확인함).
5. 주 목적은 스틱맨 동작. 3D는 쓰지 않는다.

**숫자(서버 측정)**
- 정답 왕복: 학습 22,371장, 연결 1,576,561·면 10,653 전부 복원, 렌더 차이 최대 0.64–0.72%(가장자리 안티에일리어싱).
- 토큰 길이 중앙값 376, 90% 1,970, 99% 6,033. 1판은 2,048 이하(90.5%)만, 파일당 이어진 300장까지 → 학습 15,544장, 시험 935장.
- CPU 테스트(작은 모델 1,100만 변수, 320폭, 1/16 특징, 512 토큰 이하 4,676장, 80분 5,484걸음, **비율 수정 전 16:9 레터박스 자료**)
  - 시험 다음 토큰 맞힘은 49%에서 정체, 학습은 64%까지 오름.
  - 생성은 10장 모두 문법대로 끝까지 나옴. 연결된 스틱맨과 영상 색은 따라감. 위치·자세는 못 따라감(오브젝트 맞음 0/105, 0/69, 그림 참고).
- PC 본 학습 1판: ResNet34 1/8 특징(80×45), 디코더 8층 폭 512, 5,160만 변수, bf16, 토큰 한도 묶음, 메모리 부족 시 체크포인팅. GPU는 아직 안 돌림.

**Claude가 스스로 걱정하는 것 — 각각 판정해 줘(맞다/틀리다/더 나은 방법)**
1. **늘리기 없음**: 1판은 압축 세기 말고 늘리기가 없어. CPU 테스트의 정체(학습 64% vs 시험 49%)를 보면 과적합 위험이 커. SFA 좌표 변환(이동·확대·좌우 뒤집기)은 정답이 정확히 따라 변하는데, 1판에 바로 넣어야 할까?
2. **그리는 순서의 임의성**: 같은 레이어 안의 연결 묶음 순서는 사람 파일의 DrawOrder 그대로야. 겹치지 않는 묶음끼리는 순서가 영상에 영향이 없으니 모델에게는 맞힐 수 없는 소음이야. 정답 순서를 정규화해야 할까? 한다면 렌더를 바꾸지 않는 안전한 규칙은?
3. **연결을 상대 거리 수로 분류**(포인터 머리 대신): 20 이상이 10%야. 1판으로 괜찮을까?
4. **좌표 8,192칸 분류 + 이웃 ±2칸 부드러운 정답**(0.025 단위): 회귀나 대강·세밀 두 토큰보다 나은가? 부드러운 정답을 색·굵기에도 적용한 건 맞나?
5. **위치를 못 따라간 원인**: CPU 테스트에서 모델이 영상을 덜 보고 외운 모양을 썼어. 이게 작은 모델·짧은 학습·성긴 1/16 특징·레터박스 탓인지, 구조 문제(교차 주의만으로 좌표를 읽는 것)인지 판단해 줘. 구조 문제라면 최소 수정은?
6. **8GB GPU 메모리**: 2,048 토큰 장 하나, 교차 주의 3,600칸, 8층, bf16. 체크포인팅 없이 묶음 12,288 토큰이 들어갈까? 계산으로.
7. **검증 지표**: 학습 중에는 다음 토큰 손실·맞힘만 봐. 생성 기반 오브젝트 채점을 학습 중에도(예: 1시간마다 20장) 넣어야 할까?
8. **화면 밖 오브젝트 7.7%를 정답에서 뺀 것**(경계 상자가 −30~130 밖): 장 사이 추적(2단계)에서 문제가 될까?

**봐 줄 것**
- 위 8개 판정.
- 코드 버그(파일:줄과 최소 수정). 특히 `sfa_tokens.grammar`/`encode`/`decode`의 어긋남, `seq_train.train`의 이어하기·시간 계산·메모리 부족 처리, `make_batches` 토큰 한도, `sfa_objscore`의 짝짓기·연결 F1.
- **PC 본 학습 전 필수: 있음/없음.**

출력: 짧은 표(번호 | 판정 | 근거 | 할 일) + 버그 표 + 'PC 본 학습 전 필수: 있음/없음'.
